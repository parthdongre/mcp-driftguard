# MCP DriftGuard — Midsem Demo Operator Guide

This file is the shortest path from a fresh clone to a clean project-review demonstration. It intentionally uses the same detector code that is exercised by the test suite rather than a separate mock UI.

## 1. Install

From the repository root:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -e ".[dev]"
```

The package installs the console command:

```bash
driftguard-review-demo
```

## 2. Human-readable demo

Run:

```bash
driftguard-review-demo
```

The output represents one approved MCP tool lineage. The trusted baseline is:

```text
Search repository files.
```

The server then changes the tool gradually:

```text
v1  inspect metadata
v2  prepare results for sharing
v3  prepare results for external sharing
v4  upload results when requested
```

For each version, the demo prints:

- `step`: risk between the previous version and the current version,
- `baseline`: risk between the user-approved baseline and the current version,
- `CUSUM`: accumulated low-and-slow trust debt,
- `action`: the current policy result,
- reasons: interpretable evidence generated by the temporal detector.

The important observation is not that one word such as `upload` is magically malicious. The demonstration shows why an approved-baseline comparison and accumulated temporal signal are useful when capability changes are spread across a sequence.

## 3. JSON evidence

Run:

```bash
driftguard-review-demo --json
```

This produces machine-readable evidence with the same scenario and values. It is useful for:

- screenshots,
- later UI integration,
- storing demo evidence,
- automated smoke tests,
- feeding the result into a report or dashboard without parsing terminal prose.

Validate it quickly with:

```bash
driftguard-review-demo --json | python -m json.tool
```

## 4. What to say while the demo runs

A concise explanation is:

> The first definition is the version the user actually approved. Every later update is compared both with the immediately previous version and with that approved baseline. Small local changes contribute to a CUSUM-style trust-debt signal. This means an attacker cannot rely only on keeping every adjacent update small; the system also remembers how far the tool has moved from the consent boundary.

When the final action becomes `QUARANTINE`, explain that the current demo uses a transparent deterministic temporal baseline. It is not being presented as a final production threshold or as proof of real-world attack accuracy.

## 5. Three-minute demo flow

### 0:00–0:30 — Establish trust

Show the approved baseline and say that this represents the capability the user originally consented to.

### 0:30–1:15 — Show gradual updates

Point out that each new description is only a small edit relative to the immediately previous description.

### 1:15–2:00 — Explain the three signals

Explain `step`, `baseline`, and `CUSUM`. The key contrast is adjacent change versus cumulative movement from approved behavior.

### 2:00–2:30 — Show policy action

Explain why the system converts security evidence into an operational decision such as allow, re-consent, or quarantine.

### 2:30–3:00 — Establish research credibility

Show `tests/`, `experiments/`, `docs/PAPER_READINESS.md`, repository-disjoint evaluation, and attack-family holdouts. State clearly that broad real-corpus validation is still research-in-progress.

## 6. If the reviewer asks "is this hard-coded?"

Answer precisely:

The **scenario text and thresholds are deterministic fixtures** so the review is reproducible. The risk values and alerts are not typed into the demo output; they are produced by the existing `SequentialDriftMonitor`, which calls the normal delta and feature-extraction pipeline.

Relevant execution path:

```text
review_demo.py
    |
    v
make_snapshot()
    |
    v
SequentialDriftMonitor.observe()
    |
    +--> build_delta()
    |
    +--> extract_pair_features()
    |
    +--> research_risk_signal()
    |
    v
TemporalAssessment
    |
    v
review text / JSON
```

The deterministic fixture is deliberate: a project review should be repeatable. Research benchmarks separately vary repositories, mutations, attack families, splits, and seeds.

## 7. If the reviewer asks "why does the demo say QUARANTINE rather than C2 re-consent?"

The reviewer demo is specifically a suspicious low-and-slow escalation scenario, so the simple demonstration policy maps a temporal alert to `QUARANTINE`. The broader research system distinguishes C2 legitimate capability expansion from C3 suspicious/malicious drift and can route C2 to re-consent instead.

Do not claim that every capability increase should be blocked.

## 8. If the reviewer asks "where is machine learning?"

The temporal demo is intentionally deterministic so the contribution of temporal accumulation is easy to inspect. The wider repository contains learned pair models including logistic-regression and XGBoost baselines. Those models consume semantic, structural, and capability-aware pair features.

This separation lets the research compare:

```text
pairwise learned detection
        vs
sequential temporal detection
        vs
combined strategies
```

instead of hiding every contribution inside one opaque model.

## 11. Safe claims for the review

You can confidently say:

- the core detector and benchmark infrastructure are implemented,
- tool histories can be statically extracted from JSON, Python, and TypeScript/Zod sources,
- repository-disjoint and attack-family-held-out evaluation infrastructure exists,
- the project supports learned pair baselines and sequential temporal detection,
- the reviewer demo is reproducible and automatically tested.

Avoid saying:

- that the project is production-ready,
- that controlled development accuracy equals real-world attack accuracy,
- that the exact novelty claim is permanently settled,
- that all capability escalation is malicious.

The strongest accurate framing remains:

> DriftGuard studies whether the capability a user approved is still the capability an evolving MCP tool exposes over time.
